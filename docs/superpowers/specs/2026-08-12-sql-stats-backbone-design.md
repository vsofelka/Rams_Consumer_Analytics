# SQL Backbone + Statistical Validation — Design (Phase A of 3)

## Context

The 11-task MVP (synthetic season simulator → rolling engagement score → rule-based churn view → notebooks → `docs/RESULTS.md`) is complete and pushed. This is Phase A of a three-phase follow-on, prompted by two things:

1. **The timeline was extended**, so scope deliberately trimmed for the 48-hour MVP (population size, dashboard) is back in play.
2. **Recruiter-alignment context**: the recruiter for this Rams role was interviewed and named her top three recommendations for success in data science as (1) mastering SQL, (2) performing and interpreting different types of statistical models/testing, and (3) data storytelling. The current project has none of the first two and only notebooks for the third. See `docs/DECISION_LOG.md` for the full reasoning.

The three phases, in dependency order:

- **Phase A (this doc):** SQL backbone + statistical validation — a data/analysis layer, no UI.
- **Phase B:** Streamlit dashboard — the data-storytelling deliverable, built against Phase A's SQL layer.
- **Phase C:** Scale-up to ~2,000+ fans — deferred to last since it's just parameters once A and B exist, and doing it last avoids re-running an expensive regeneration cycle while A and B are still being built.

Real historical data was considered and explicitly deferred (see Decision Log) — the planted-churn cohort is what makes the current validation honest (known ground truth), and no concrete real dataset is in hand yet. The synthetic simulator remains the core for all three phases.

## Goals

- Add a real SQL layer that is load-bearing (not decorative): the actual pipeline writes to it, and downstream analysis genuinely queries it.
- Add statistical rigor the project currently lacks: is the planted-churn cohort's decline real, and is the churn rule's performance better than chance — proven with tests, not eyeballed.
- Document reasoning as it happens (decision log, notebook markdown, `RESULTS.md`) so the project owner can explain every choice later without re-deriving it.

## Architecture & Data Flow

```
season_simulator ─┐
                   ├─→ scoring (engagement.py, churn.py) ─→ scripts/run_season.py ─┬─→ data/weekly_snapshots/*.csv  (unchanged)
                   │                                                                └─→ data/fan_analytics.db (SQLite, new)
                   │
                   └─→ scoring/validation.py (existing) + scoring/stats.py (new) ─→ notebooks/04_sql_analysis.ipynb
```

- `scripts/run_season.py` gains one addition: after writing each week's CSV (existing behavior, untouched — existing tests keep passing), it also writes that week's data into a SQLite database at `data/fan_analytics.db` (gitignored, same convention as `data/weekly_snapshots/` — regenerated by running the script, never committed).
- `notebooks/04_sql_analysis.ipynb` reads **only** from the SQLite database — never re-runs the simulator or scoring code directly, same decoupling principle the existing three notebooks already follow.

## Schema

Two tables, mirroring the existing CSV structure:

- **`fans`** (dimension table): `fan_id` (PK), `tenure_years`, `plan_tier`, `baseline_engagement`, `is_planted_churn`, `decline_start_week`
- **`weekly_snapshots`** (fact table): `fan_id` (FK → `fans.fan_id`), `week`, `engagement_score`, `tier`, `at_risk` — one row per fan per week, composite key `(fan_id, week)`

## SQL Engine

**SQLite** — built into Python's standard library, zero extra dependency, single `.db` file, universally recognized. The SQL written is standard regardless of engine; SQLite was chosen over DuckDB (the other embedded, zero-server option considered) for maximum simplicity and portability — anyone cloning this repo can run it with nothing extra installed.

## Statistical Validation (`scoring/stats.py`)

New module, pure functions, unit-tested — same pattern as `engagement.py` / `churn.py` / `validation.py`. Three distinct techniques, deliberately chosen to fit what's actually being tested (the "interpret different types" story):

1. **Mann-Whitney U test** — is the planted-churn cohort's engagement score significantly lower than everyone else's by the final week? Chosen over a t-test because `engagement_score` is a percentile rank by construction (not normally distributed), and Mann-Whitney doesn't assume normality.
2. **Wilson score confidence interval** — a CI around the churn rule's precision and recall. A naive normal-approximation CI can misbehave with small counts (13 flagged, 25 planted) near 0/1; Wilson handles that correctly.
3. **Hypergeometric test** — the exact probability of catching ≥8 true churners by chance, given 25 true churners in a population of 300 and 13 fans flagged. Matches the actual sampling process (drawing without replacement from a finite population) exactly, rather than approximating with a binomial.

## SQL Notebook (`notebooks/04_sql_analysis.ipynb`)

Reads from `data/fan_analytics.db` only. Contents:

1. Load `fans` and `weekly_snapshots` via SQL, `SELECT` + basic filtering.
2. A window-function query (`LAG() OVER (PARTITION BY fan_id ORDER BY week)`) computing each fan's week-over-week score delta.
3. A `GROUP BY` aggregation of average engagement by plan tier and week.
4. A CTE-based SQL query that reconstructs the at-risk list from Notebook 03 directly in SQL (join `fans` + `weekly_snapshots`, filter `at_risk = 1` at the final week) — the same result arrived at two ways, as a cross-check.
5. Calls into `scoring/stats.py` to run and print the three statistical tests above, each preceded by a markdown cell explaining in plain language why that test was chosen and what the result means.
